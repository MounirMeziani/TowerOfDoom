# Olsen Tower of Doom — Build Plan

## What it is
A fast, mobile-first browser game that teaches Olsen Consulting's **2 A's of Feedback**:
- **Giving feedback:** **Assist** (offer helpful, constructive ideas to support improvement instead of reacting from frustration or anger) and **Actionable** (clear, concrete steps the person can act on).
- **Receiving feedback:** **Appreciate** (say "thank you", even when it's uncomfortable or you disagree) and **Accept or Decline** (reflect, weigh its value, and make an autonomous choice about what to implement).

Players climb a 12-floor office tower overrun by feedback villains. Built for a live team workshop: a host projects a session code + QR, everyone plays on their phone, and a live leaderboard updates in real time.

## Game loop
- 12 floors per run: floors 1-5 and 7-11 are regular floors (alternating giving / receiving, drawn at random from a pool of 24), floor 6 is a **receiving boss**, floor 12 is a **giving boss**.
- Regular floors are all **choose**: a 1-2 sentence scenario, one short question and exactly 3 answers (the two wrong ones each fail a different A). The old "spot" floors were rewritten as choose floors.
- Boss floors: the player writes a free-text response; an AI judge (Vercel AI Gateway, with a deterministic heuristic fallback) scores each A from 0-2 and gives a short coaching tip; an exemplar answer is shown.
- 3 hearts. A wrong answer, a timeout (45s regular / 180s boss), or a failed boss costs a heart. 0 hearts = DOOMED. Surviving floor 12 = VICTORY.
- Scoring: 100 per correct answer + streak bonus (+25 per consecutive correct answer, capped at +100) + speed bonus (up to +50 if fast); boss: 75 per A-point + 100 if passed; victory: +150 per heart left. Max 3750.
- After every answer: a reveal panel explains why, with badges showing which A's were hit or missed.
- End screen: score, floors cleared, per-A mastery bars, your rank, and links to replay, view the leaderboard, or learn.

## Workshop flow: character creation + waiting lobby
1. The host opens `/host`, names the session, and gets `/host/[code]` in **LOBBY** state: a giant join code, a QR code for `/?s=CODE`, and a live grid of players as they join (hero avatar + name, with a pop-in animation and a "N heroes ready" count). The host is the only one who sees a **Start the Climb** button, which is protected by a secret host key stored in their browser.
2. A player scans the QR or clicks the link and lands on `/?s=CODE` with a "Joining session CODE" chip. They **create a character**: a name (1-24 characters) plus one of 8 office-adventurer heroes (emoji avatar, title, color, a one-line perk), with a live preview card. Then they enter the lobby.
3. `/lobby/[code]` is the **waiting room**: a 3D lobby hall where every player walks around and sees everyone else's hero move in real time (see "3D game"), with a minimal overlay (code, 👥 count, pulsing ⏳, hero / 2D / leave icons). The 2D fallback is a live grid of heroes.
4. When the host presses Start, the session status changes to `playing` and every lobby client gets a countdown (3-2-1-CLIMB!) and is sent to `/play` at the same moment (realtime broadcast for an instant start, plus a 2s status poll as a fallback). Anyone who joins after the start skips the lobby and goes straight to `/play`.
5. During play, each player's presence updates with their floor, score and hearts, so the host view switches to a **live race** (everyone's hero climbing a tower graphic) next to the live leaderboard and team mastery. The host can End the session, which sets status `ended`.
6. Solo players with no session code skip the lobby: they create a character, then go straight to `/play`.
7. **Admin instance:** `/admin` (an alias of `/host`, labelled "Admin" in the nav) is where the facilitator creates and controls a session. Admin powers are Start the Climb, End session, and Reset to lobby (for a second round). They require the session's secret host key, which is saved in the creating browser. The admin view has a "Copy admin link" (`/host/CODE?k=HOSTKEY`) so the facilitator can run the controls from a phone or laptop while the projector shows the same page in spectator mode. Opening that link saves the key in that browser and strips it from the URL. Without the key, `/host/CODE` is a read-only spectator or projector view.

## Pages
- `/`: landing page with tower art and the character creator (name + hero picker, session code prefilled from `?s=CODE`). The button reads "Enter the Lobby" when there's a code and "Climb the Tower" otherwise.
- `/lobby/[code]`: the waiting room (see above).
- `/play`: the game. It shows the player's hero in the HUD. If the player's session is still in `lobby` status, they are redirected to the lobby.
- `/learn`: the 2 A's reference card with good and bad examples (printable).
- `/leaderboard` (`?s=CODE` optional): realtime top scores, global or per session.
- `/host`: create a session. `/host/[code]`: projector view. In LOBBY state it shows the join code, the QR code, the live player grid and the Start button. In PLAYING state it shows the live race, the live leaderboard, the player count and team mastery per A (the "team's weakest A"), plus an End button.

## Backend
- Supabase tables: `sessions(code, name, status lobby|playing|ended, started_at, host_key)` and `runs(player, avatar, score, floors, hearts, duration, outcome, a_stats jsonb, session_code)`. RLS: public read-only, and `host_key` is not readable by the public. All writes go through Next.js route handlers using the secret key. Realtime is on for `runs`. The lobby uses Realtime Broadcast on channel `lobby:CODE` and needs no tables: `status` (admin start/end/reset), `who` (roster beacons: each player's name/hero/phase/floor/score/hearts, sent on join, on change, on a `hello`, and every max(5s, N x 0.5s); stale after 20s+; `bye` on leave) and `pos` (3D positions). Supabase Presence is switched off (`USE_PRESENCE` in `src/lib/lobby.ts`) because presence-enabled channels on this project hit server-side `channel_crash` errors that left clients deaf for seconds at a time. 3D `pos` traffic is held to a fan-out budget of `NEXT_PUBLIC_RT_FANOUT_BUDGET` deliveries per second per session (default 250), so each player's move interval is about 1.6s at 20 players, 3.6s at 30 and 6.4s at 40 (remote heroes glide in between). Full-speed movement for 30-40 players needs a Supabase plan or Realtime limit above the free tier's 100 msg/s and 2M msgs/month; on such a plan set the budget to about 2000.
- API routes: `POST /api/sessions` (returns hostKey), `GET /api/sessions/[code]`, `POST /api/sessions/[code]/start` and `/end` (require hostKey), `POST /api/runs` (zod validation, score clamped to MAX_SCORE, best-effort per-IP rate limit, returns rank), `POST /api/judge` (AI SDK + AI Gateway, prompt-injection-safe, with heuristic fallback).
- Deploy: GitHub `MounirMeziani/TowerOfDoom` -> Vercel project `olsentowerofdoomtemp` (team zune-labs) -> https://olsentowerofdoomtemp.vercel.app

## 3D game
The whole game is a 3D world (three.js + @react-three/fiber 9 + drei 10), built only from primitives (no model or texture downloads), with a dark-purple night palette, ember/gold accents, fog and fake blob shadows. All 3D code is client-only and loaded with `next/dynamic({ ssr: false })`, so `/`, `/learn` and `/leaderboard` ship no three.js.

- **Code layout:** `src/components/three/kit` (GameCanvas, HeroModel, movement controller, FollowCamera, TapToMove, VirtualJoystick, debug hook), `src/components/three/world` (LobbyHall, FloorRoom, SenseiModel, VillainFigure, SpeechBubble, TowerCutaway, SkyBackdrop), `src/components/lobby3d` (3D lobby + remote heroes), `src/components/climb3d` (the climb scene and its pure state machine `climbFlow.ts`), `src/lib/motion-sync.ts` (position sync), `src/lib/three/support.ts` (WebGL check + 2D toggle, safe for light pages).
- **Lobby (`/lobby/[code]`):** a tower lobby hall (marble floor, pillars, reception desk, elevator with a glowing "12", storm window with the doom eye). Every player walks around freely and sees everyone else's hero move live. Positions go over the shared `lobby:CODE` channel as `pos` broadcasts (`{ id, h, x, z, r, m }`), sent only on change, max 5 Hz per player, with the interval stretched to keep the whole session under ~60 msgs/s, plus a 3s heartbeat. Remote heroes are interpolated and hidden after 15s of silence. The overlay is minimal: code, 👥 count, a pulsing ⏳, and icon buttons for hero, 2D and leave. On Start: movement freezes, the elevator doors open, a 3-2-1 countdown plays, then `/play`.
- **Climb (`/play`):** each floor is a room themed by its department (desks, monitors, cabinets, plants, whiteboards; boss floors 6 and 12 are an ember-lit boardroom with a gold GRAND SENSEI). The player spawns at the front and walks up to the sensei at the back. Within `TALK_RADIUS` the sensei turns, says a 1-2 word line, the camera eases into a two-shot and the question opens as a DOM sheet (bottom sheet on phones, right column on wide screens). The floor timer starts only when the question opens (the 3D layer defers the engine's START / NEXT until then), so walking never costs time or speed bonus. Movement is frozen while the question or reveal is open. After the reveal the stairs in the back corner light up; walking into them fades to the next room. Lost hearts raise lava in the room. The floor's villain stands silently on a pedestal as flavour. The finish screen is the existing DOM results over a 3D rooftop (victory) or lava (doom) backdrop.
- **Question panel (2D and 3D):** only a mode icon (🗣 giving / 👂 receiving), the scenario, one question and the answer buttons. No villain names, departments, taunts or quote bubbles. Reveal: ✓/✗ + points + one sentence + the A badges. Boss: scenario + "Write what you'd say." + a text box; result = per-A pips + one sentence.
- **Controls:** WASD / arrow keys, click or tap the floor to walk there (press and drag to steer), a virtual joystick on touch screens (bottom left, coarse pointers only), and **E / Enter or the 💬 button to auto-walk** to the sensei (or ⬆ to the stairs), so nobody is blocked by movement. Keys 1-4 and Enter still answer. Keys are ignored while typing in a field.
- **Host (`/host/[code]`, projector):** LOBBY state shows the giant code + QR next to a slow overhead camera of the same lobby hall with every hero walking live (observer only; players without a live position stand at a spawn point). PLAYING state shows a 12-floor tower cutaway (orthographic, fits 1920x1080) with each hero on their current floor, gliding up as they climb, a crown on the roof for victory and a fallen grey hero with 💀 for doom, next to the live leaderboard and team stats.
- **Performance:** dpr [1, 1.5] dropping to 1 via PerformanceMonitor, no shadow maps or post-processing, shared geometries/materials, roughly 80-150 draw calls per scene.
- **2D fallback:** if WebGL is unavailable, the 3D scene crashes, or the player picks 2D (☰ menu or the 2D button; stored in localStorage `tod.mode2d`), the original 2D lobby grid, game and host race views are used. All question UI is real DOM in both modes.
- **Test hook:** scenes write `window.__TOD__ = { scene, self, remoteCount, rosterCount, remotes, floor, nearSensei, questionOpen }` (max ~5 updates/s) for Playwright.

## Build process (multi-agent workflow)
Foundation (3 parallel) -> Build (6 parallel: content, game, multiplayer/admin, lobby, landing/character, judge) -> Integrate -> Review (6 lenses + adversarial verification) -> Fix (parallel per area) -> Ship (deploy + production E2E).
